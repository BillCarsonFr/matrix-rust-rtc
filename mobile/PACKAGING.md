# Mobile Packaging Documentation

This directory contains scripts and configuration for building and packaging the Matrix RTC FFI library for Android and iOS.

## Structure

```
mobile/
├── android/
│   ├── gradle/
│   │   └── wrapper/
│   │       └── gradle-wrapper.properties
│   ├── matrixrtc/
│   │   ├── src/main/
│   │   │   ├── AndroidManifest.xml
│   │   │   └── jniLibs/        (generated by build script)
│   │   ├── build.gradle
│   │   ├── proguard-rules.pro
│   │   └── consumer-rules.pro
│   ├── build.gradle
│   ├── settings.gradle
│   └── gradlew
├── ios/
│   ├── build/                  (generated by build script)
│   │   ├── MatrixRtcFFI.xcframework   (with Headers/MatrixRtcFFI/module.modulemap)
│   │   ├── MatrixRtcFFI.xcframework.zip (+ .sha256, with --zip)
│   │   └── generated/, headers/       (intermediate)
│   ├── generated/              (generated by build script: MatrixRtc.swift)
│   └── Debug-Package.swift     (local-development twin of the root Package.swift)
```

Binding names (`org.matrix.rtc` for Kotlin, `MatrixRtc` / `MatrixRtcFFI` for
Swift) are pinned in `crates/matrix-rtc-ffi/uniffi.toml`.

## Consuming a release

Releases are tagged `v<version>` and ship the **media** variant only (the slim
build below is for development). How they are produced is in
[../RELEASING.md](../RELEASING.md).

### Android

The AAR is a Maven artifact, `io.github.billcarsonfr.matrixrtc:matrix-rtc-android`.
It is published to the repository's GitHub Packages Maven repository on every
release, and to Maven Central once that is configured (then the extra
repository block below is unnecessary).

```kotlin
// settings.gradle.kts — only needed while consuming from GitHub Packages,
// which requires a GitHub token with read:packages.
dependencyResolutionManagement {
    repositories {
        maven {
            url = uri("https://maven.pkg.github.com/BillCarsonFr/matrix-rust-rtc")
            credentials {
                username = providers.gradleProperty("gpr.user").orNull ?: System.getenv("GITHUB_ACTOR")
                password = providers.gradleProperty("gpr.key").orNull ?: System.getenv("GITHUB_TOKEN")
            }
        }
    }
}

// build.gradle.kts of the app or module
dependencies {
    implementation("io.github.billcarsonfr.matrixrtc:matrix-rtc-android:<version>")
}
```

The POM declares JNA (`net.java.dev.jna:jna@aar`) as a compile dependency, and
the AAR bundles `libwebrtc.jar` and the three ABIs (`arm64-v8a`, `armeabi-v7a`,
`x86_64`). Call `MatrixRtc.initialize()` before anything else — see
[README.md](README.md). Consumer ProGuard rules ship in the AAR.

### iOS

In Xcode, *File > Add Package Dependencies…*, enter this repository's URL and
pick a `v*` tag (the `MatrixRtc` product). Then add `-ObjC` to the app target's
*Other Linker Flags* — libwebrtc's Objective-C categories are dead-stripped from
the static archive otherwise and the app aborts at runtime with
`+[NSString stringForAbslStringView:]: unrecognized selector`. The simulator
slice is Apple Silicon only.

```swift
import MatrixRtc
```

The package's `Package.swift` downloads `MatrixRtcFFI.xcframework.zip` from the
tag's GitHub Release (checksum pinned in the manifest) and compiles the generated
Swift in `Sources/MatrixRtc` against it. An app that also links matrix-rust-sdk's
`MatrixRustSDK` package links two Rust static libraries; both are built with the
current stable toolchain, which links cleanly. If a duplicate-symbol error ever
appears, report it — the fallback is shipping a dynamic framework instead.

## Android AAR Build

To build the Android AAR library:

```bash
./scripts/build-android-aar.sh
```

This script will:
1. Install `cargo-ndk` if needed
2. Add required Rust targets
3. Build native libraries for arm64-v8a, armeabi-v7a, and x86_64
4. Generate Kotlin bindings from UniFFI
5. Build the AAR using Gradle

**Output:** `mobile/android/matrixrtc/build/outputs/aar/matrixrtc-release.aar`

### Prerequisites

- Android NDK (set via `$ANDROID_NDK_HOME` or `$ANDROID_HOME/ndk/<version>`)
- JDK 8 or higher
- Rust with targets: `aarch64-linux-android`, `armv7-linux-androideabi`, `x86_64-linux-android`

### Usage of a locally built AAR

Released AARs come from Maven (see [Consuming a release](#consuming-a-release));
to try a local build directly:

```gradle
dependencies {
    implementation files('../path/to/matrixrtc-release.aar')
    implementation 'net.java.dev.jna:jna:5.19.1@aar'
}
```

The build script accepts `--target <triple>`, `--profile <name>`,
`--split-debug`, `--skip-build`, `--skip-codegen` and `--version <v>`; run it
with `--help`. The AAR's version is the workspace version from `Cargo.toml`
unless `--version` (Gradle `-PmatrixRtcVersion`) overrides it.

## iOS XCFramework Build

To build the iOS XCFramework:

```bash
./scripts/build-ios-xcframework.sh
```

This script will:
1. Add required Rust targets for iOS
2. Build static libraries for:
   - `aarch64-apple-ios` (device)
   - `aarch64-apple-ios-sim` (simulator arm64)
   - `x86_64-apple-ios` (simulator x86)
3. Create a universal simulator library
4. Generate the Swift bindings, header and module map from UniFFI
5. Create the XCFramework, with the header and module map in each slice under
   `Headers/MatrixRtcFFI/` so `import MatrixRtcFFI` resolves

**Output:**
- XCFramework: `mobile/ios/build/MatrixRtcFFI.xcframework`
- Swift bindings: `mobile/ios/generated/MatrixRtc.swift` (`--swift-out <dir>`
  to put them elsewhere; the release passes `Sources/MatrixRtc`)
- With `--zip`: `MatrixRtcFFI.xcframework.zip` and its `.sha256` next to it

### Prerequisites

- Xcode (with command-line tools)
- Rust with targets: `aarch64-apple-ios`, `aarch64-apple-ios-sim`, `x86_64-apple-ios`

### Usage of a locally built XCFramework

Released builds are consumed as a Swift package (see
[Consuming a release](#consuming-a-release)). For a local build:

```bash
./scripts/build-ios-xcframework.sh --swift-out Sources/MatrixRtc   # add MEDIA=1 for media
cp mobile/ios/Debug-Package.swift Package.swift                    # do not commit
```

then add the repository as a *local* package in Xcode. `Debug-Package.swift`
points the binary target at `mobile/ios/build/MatrixRtcFFI.xcframework`
instead of a released zip. Alternatively, link the xcframework by hand and copy
`mobile/ios/generated/MatrixRtc.swift` into the app.

## Full Build Workflow

To build both Android AAR and iOS XCFramework:

```bash
# Install tools (the bindings generator is the in-repo uniffi-bindgen crate)

# Build for Android
./scripts/build-android-aar.sh

# Build for iOS

```

## The `media` Variant (frame streams, publishing, constraints)

Both scripts accept `MEDIA=1` (or use `make build-android-media` /
`make build-ios-media`), which builds `matrix-rtc-ffi` with its `media`
feature: participants with observable audio/video frame streams, local
publishing, per-stream constraints, and the MSC4195 multi-SFU connection
pool — with no LiveKit types on the API surface. The default build stays
the slim signalling-only artifact.

**What changes with `MEDIA=1`:**

| | slim | media |
| --- | --- | --- |
| LiveKit client + libwebrtc | no | statically linked |
| Binary size per ABI | ~1–2 MB | expect **+8–15 MB** (fill in measured numbers below) |
| Build prerequisites | Rust targets | + C++ toolchain (NDK ≥ r25 / Xcode), network on first build (webrtc-sys downloads the prebuilt libwebrtc) |
| Android extras | — | `libwebrtc.jar` bundled into the AAR (the native code up-calls into its Java classes); `JNI_OnLoad` initialises libwebrtc automatically when the library loads |
| iOS extras | — | the **app must add `-ObjC` to "Other Linker Flags"** — libwebrtc's Objective-C categories are dead-stripped from the static archive otherwise and abort at runtime (`+[NSString stringForAbslStringView:]`); if `-ObjC` causes duplicate symbols, use `-force_load` on the archive instead. **Simulator is Apple Silicon only**: livekit publishes no libwebrtc for the Intel (x86_64) iOS simulator, so the media xcframework contains arm64 device + arm64 simulator slices (the slim variant keeps the universal simulator) |

**Measured sizes** (record here after each release build — both scripts
print them):

| ABI / slice | slim | media (`release`) | media (`mobile-release`, as released) |
| --- | --- | --- | --- |
| android arm64-v8a | _measure_ | 23 MB `.so` (2026-07-31) | 19 MB `.so` stripped + 55 MB `.so.debug` (2026-09-06) |
| android armeabi-v7a | _measure_ | 14 MB `.so` (2026-07-31) | 11 MB `.so` stripped + 51 MB `.so.debug` (2026-09-06) |
| android x86_64 | _measure_ | 27 MB `.so` (2026-07-31) | 23 MB `.so` stripped + 52 MB `.so.debug` (2026-09-06) |
| android AAR | _measure_ | — | 26 MB (2026-09-06) |
| ios arm64 (device) | _measure_ | 519 MB `.a` — **pre-link archive, see note** (2026-07-31) | 257 MB `.a` after `strip -S` (849 MB with DWARF) (2026-09-06) |
| ios arm64 (simulator) | _measure_ | 520 MB `.a` — pre-link archive (2026-07-31) | 257 MB `.a` after `strip -S` (2026-09-06) |
| ios xcframework zip | — | — | 129 MB (400 MB with DWARF, `--keep-debug`) (2026-09-06) |

### Reading the iOS sizes (why the `.a` is ~520 MB and why that's fine)

The Android and iOS numbers in the table measure **different things**:

- The Android `.so` is a **linked** shared library: symbols resolved, dead
  code stripped, one binary — that *is* the shipped cost.
- The iOS `.a` is an **unlinked static archive**: a container of every
  object file the linker *might* need. The bulk is livekit's prebuilt
  `libwebrtc.a` for iOS (itself several hundred MB of object code as
  released), plus the object files of every Rust dependency. Nothing has
  been dead-stripped, because with a static library that's the *consuming
  app's* link step, not ours.

When an Xcode project links against `MatrixRtcFFI.xcframework`, only the
symbols the app actually reaches are pulled in and the rest is discarded.
The real shipped cost is the **app binary delta**, expected to be in the
same tens-of-MB range as the Android `.so`. This is the normal shape for
any iOS library carrying libwebrtc — livekit's own artifacts look the same.

**How to measure the real cost** (record the result in the table above):

1. Create a minimal iOS app target; archive it and note the App Store
   thinned size (or the `.app` binary size) — that's the baseline.
2. Link `MatrixRtcFFI.xcframework`, add `-ObjC` to "Other Linker Flags",
   call one FFI symbol so the linker can't drop everything, re-archive.
3. The difference between the two is the number that belongs in the table.

**One honest caveat:** `-ObjC` forces the linker to load every object file
in the archive that contains Objective-C — weakening dead-stripping for
those objects specifically. That is why the delta should be measured
rather than assumed. If it comes out worse than expected, the fallback is
`-force_load` on the archive combined with a version-script-style export
list. The released archives are already built with the `mobile-release`
profile (`opt-level = "s"`, LTO) and stripped of DWARF (`strip -S`, symbol
names kept — crash reports resolve to Rust function names, not lines);
`--keep-debug` keeps the DWARF for local debugging. `opt-level = "z"` is the
remaining knob.

Benign build noise with `MEDIA=1`: uniffi-bindgen warns about a missing
`ktlint` (formatting only). The Android module tells AGP not to strip the
`.so` (`keepDebugSymbols`): the build script strips it itself and leaves a
`.gnu_debuglink` to the split `.so.debug` in `mobile/android/debuginfo/`.

**Host app responsibilities with media** (see the module docs in
`crates/matrix-rtc-ffi/src/media/mod.rs` for the full flow):

- Join the slot through the manager first, then call
  `connectMediaSession(manager, config, tokenProvider)`.
- Implement `OpenIdTokenProvider` with your Matrix client (it is called for
  peers' foci too).
- Feed decrypted `m.rtc.encryption_key` to-device messages to
  `manager.receiveEncryptionKey(...)`; outbound keys already flow through
  your `CommandSenderCallback`. Keys that arrive before
  `connectMediaSession` are replayed into the transport on attach, so the
  order of "join, receive keys, connect media" does not matter.
- Include `transports_json` on the sticky events you feed in — without it
  peers project as media-unreachable.
- Render frames from `videoStream(...).next()`: either the safe `data(plane)`
  copies, or zero-copy via `planePtr(plane)`/`stride(plane)`/`planeLen(plane)`
  while holding the frame object.

**Smoke test** (no SFU or homeserver needed; compiles libwebrtc):

```bash
make test-ffi-media
```

## Environment Setup

### Android NDK

Set the Android NDK location:

```bash
export ANDROID_NDK_HOME=/path/to/android-ndk
# or
export ANDROID_HOME=/path/to/android-sdk
```

The build script will auto-detect from `$ANDROID_HOME/ndk/<version>` if not explicitly set.

### Rust Targets

Ensure all required Rust targets are installed:

```bash
# iOS
rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios

# Android
rustup target add aarch64-linux-android armv7-linux-androideabi x86_64-linux-android
```

## Troubleshooting

### Android Build Fails

- Check that `ANDROID_NDK_HOME` is set correctly
- Verify Rust targets: `rustup target list | grep android`
- Run `./gradlew clean` before retrying
- `MEDIA=1` + `failed to run llvm-readelf: ... NotFound` from `webrtc-sys`:
  webrtc-sys locates the NDK by joining `toolchains/llvm/prebuilt/...` onto
  `ANDROID_NDK_HOME` *verbatim* — it doesn't handle the `ndk/` parent-dir
  convention that gradle and cargo-ndk accept, so plain compilation can
  succeed while this step fails. The build script normalises this for you:
  it accepts `ANDROID_NDK_HOME` pointing at either a versioned NDK or the
  `ndk/` parent (highest version wins), falls back to
  `ANDROID_NDK_ROOT`/`ANDROID_HOME`/default SDK paths, exports the resolved
  versioned path *for the build only*, and preflights `llvm-readelf` with a
  clear error. Your own environment does not need to change.

### iOS Build Fails

- Verify Xcode command-line tools: `xcode-select --install`
- Check Rust targets: `rustup target list | grep apple`
- The Swift bindings come from the in-repo `uniffi-bindgen` crate (`cargo run
  -p uniffi-bindgen`); a globally installed `uniffi_bindgen` is not used and
  its version does not matter

## Publishing and CI

Releases are cut by `.github/workflows/release.yml`; the procedure, secrets
and coordinates are in [../RELEASING.md](../RELEASING.md). The per-commit CI
builds of both variants are `.github/workflows/build-mobile.yml` (slim) and
`build-mobile-media.yml` (media); they upload the artifacts as workflow
artifacts only.
